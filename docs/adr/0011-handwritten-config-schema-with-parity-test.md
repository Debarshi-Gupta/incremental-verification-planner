# ADR 0011: Hand-maintained JSON Schema with an automated schema↔defaults↔runtime parity test (schema generation deferred)

## Status

Accepted

## Context

The LLD requires that configuration be YAML with strict unknown-field rejection and that "JSON Schema is published for editor validation" (LLD §2.2 line 77), that the §5.2 example be "schema-complete" with "a matching JSON Schema and validation tests" whose code defaults are implemented too (line 399), and that unknown keys are errors (line 272). The strategy review found the schema unwired and drifting: "`schemas/ivp-config.schema.json` is referenced by no code; the shipped default config fails its own schema; constraint caps diverge (excerpt bytes, calibration minimums). Generate or test the schema against `config.Defaults()` and the §5.2 example in CI" (`docs/implementation-completion-strategy.md` §3.2.9), and §3.5.1 lists a "schema-generation strategy" ADR as required.

Before this change the schema and the runtime had drifted in three ways: the shipped `config/default-config.yaml` and `internal/cli/default-config.yaml` omitted keys that exist in the `Config` structs (`history_window_days`, `failure_retry_count`, `critical_path_patterns`, `documentation_path_patterns`, and `coverage_paths` on six adapters); value bounds in the schema diverged from `config.Validate()` (e.g. `max_excerpt_bytes`, `minimum_calibration_runs`, coverage floors); and several `Validate()` rules had no schema counterpart. `go.mod` contains no JSON-Schema library (`invopop/jsonschema`, `santhosh-tekuri/jsonschema`, etc.).

## Decision

- **The schema stays hand-maintained; drift is prevented by an automated parity test instead of generation.** The gate is `internal/config/schema_parity_test.go`, which runs under `go test ./...` locally and in CI (`.github/workflows/ci.yml:39`, `-race`).
- **The parity contract is exactly:**
  1. **Key-tree parity.** The schema's property tree equals the yaml-tag tree of the Go `Config` structs, leaf-for-leaf (arrays are leaves), in both directions — `TestSchemaMatchesConfigStructTree` (`schema_parity_test.go:353`).
  2. **Unknown keys are errors.** Every object node in the schema sets `additionalProperties: false`, enforced structurally by the same test (LLD line 272).
  3. **No `required` arrays anywhere.** An absent key means "use the product default" (LLD precedence layer 1, line 266); the §5.2 example legitimately omits keys such as `execution` and `analysis.history_window_days` (line 399 declares it schema-complete), and requiring every key would contradict that. Presence/absence is therefore never a validity axis; *values* are.
  4. **Value bounds in the schema ≡ `config.Validate()` bounds.** Enforced boundary-by-boundary in `TestSchemaAndRuntimeValidationAgreeOnBoundaries` (`schema_parity_test.go:540`): ~40 cases feed each document to both the schema evaluator and `Decode`+`Validate` and assert both reach the expected verdict — including the tightened conservative rules (`modes.observe.execute_full_suite`, `modes.fast_feedback.final_ci_full_suite_required`, and `safety.audit.quarantine_on_confirmed_miss` must be `true`; `telemetry.capture_raw_stdout` must be `false`; calibration/audit minimums ≥ 1) at `validate.go:48,51,92,110,54,89`.
  5. **Every shipped and documented configuration validates.** `config.Defaults()` marshalled to JSON (`schema_parity_test.go:367`), both shipped templates, and the LLD §5.2 example extracted from the document itself (`schema_parity_test.go:382`) must all pass the schema. A fourth test asserts both templates are key-complete against the struct tree and key-identical to each other (`schema_parity_test.go:431`).
  6. **Semantic rules live in `Validate()` only** — glob syntax, argv safety, URL shape beyond its pattern, and cross-field ordering are runtime concerns the schema does not attempt; the schema documents structure and scalar bounds, `Validate()` enforces product safety.
  7. **Safety default *values* match the LLD §5.2 example.** `TestSafetyDefaultsMatchLLDExampleAndShippedTemplates` (`schema_parity_test.go:487`) compares `safety.hard_full_suite_paths`, `safety.hard_full_suite_risk_labels`, and `safety.always_run_check_ids` as sets across four sources — the example extracted from the LLD, `config.Defaults()`, `config/default-config.yaml`, and `internal/cli/default-config.yaml`. Rules 1-5 compare keys and bounds only, and the schema carries no literal defaults (rule 6), so without this rule a shipped template could silently drop hard-full-suite triggers; during Wave 1 review the CLI template in fact shipped a condensed 16-glob list missing `**/gradle/libs.versions.toml` and `**/gradle-wrapper.properties`, which this test now fails on.
- **`config.Defaults()` now returns empty slices, not nil, for `CriticalPathPatterns`, `DocumentationPathPatterns`, and six adapters' `CoveragePaths`** (`defaults.go:32-43`). A nil slice marshals to JSON `null`, which fails the schema's `type: array`; all consumers are `len()`-based, so the change is behavior-preserving, and empty `[]` correctly means "no patterns configured".
- **The test suite uses a purpose-built evaluator for exactly the assertion keywords the schema employs** (`$ref`, `type`, `enum`, `const`, `properties`, `additionalProperties`, `items`, `minimum`, `maximum`, `exclusiveMinimum`, `minLength`, `minItems`, `pattern`; `title`/`description`/`default` are annotations). Adding a schema keyword outside that set without extending the evaluator fails loudly in the boundary test rather than silently skipping enforcement.
- **Trigger to switch to generation:** a second published schema for the same config, or the config surface growing faster than hand-maintained bounds can be reviewed. At that point generate from the Go structs with a reviewed filter for descriptions/examples and keep this same parity test as the gate (generation replaces the writer, not the contract). LLD line 77 mandates a *published, editor-usable* schema — which is why documentation quality, not just correctness, is part of the hand-maintained choice.

## Alternatives considered

1. **Generate the schema from the Go structs (`invopop/jsonschema`).** Rejected for now: generated output encodes Go's view (field-name tagging artifacts, no product-level descriptions, defaults, or LLD cross-references) and the LLD requires a schema published for *editor validation*, i.e. a documented artifact. Generation also cannot express contract rule 3 (no `required`) or rule 6 (semantics excluded) without a customized wrapper — at which point the wrapper plus generation is more moving parts than schema + parity test. Re-evaluated only under the trigger above.
2. **Leave the schema hand-maintained with no test** (status quo ante). Rejected: this is exactly strategy gap §3.2.9 — the shipped defaults failed the published schema and nobody noticed.
3. **Drive the boundary test with a full JSON Schema validator dependency** (e.g. `santhosh-tekuri/jsonschema`). Rejected for this wave to keep `go.mod` free of a runtime-adjacent dependency for what is a fixed, known keyword subset; the mini-evaluator fails the test if an unsupported keyword appears, so safety is preserved. Revisit if the schema adopts `allOf`/`if-then`/`patternProperties`, which the hand-rolled walker deliberately does not implement.
4. **Relax the schema (drop diverging bounds) instead of tightening `Validate()`.** Rejected in the conservative direction: for bounds like `minimum_calibration_runs ≥ 1` and the must-be-true safety flags, the stricter runtime rule is the safer product behavior (LLD §7.2/§10 gating), so the schema was brought up to `Validate()` — never the reverse — and each tightening is asserted on both sides of the boundary table.

## Consequences

The published schema, the shipped templates, the product defaults, the LLD §5.2 example, and `config.Validate()` are now a single tested unit: any config-surface change that touches one without the others fails `go test ./...` locally and in CI. The historical drift (failing shipped default, diverging caps) is closed and verified by the boundary table rather than by review alone. Editors consuming `schemas/ivp-config.schema.json` get strict unknown-key errors with bounds that match what `ivp doctor`/`ivp init` actually enforce, so a config accepted by the editor validates at runtime and vice versa. The remaining deliberately-unenforced items (glob/argv/URL semantics, cross-field ordering) are documented as `Validate()`-owned here so no inventory row treats their absence from the schema as drift.
